Linux für Cybersecurity: Befehle, die Security-Profis wirklich brauchen

Linux ist nicht nur eine Plattform für Server und Security-Tools. Die Shell liefert direkt die Informationen, die bei Netzwerkdiagnose, Incident Response, Forensik und System-Hardening entscheidend sein können.

Wer Linux in der Cybersecurity professionell einsetzen möchte, sollte nicht möglichst viele Befehle auswendig kennen, sondern verstehen, welche Information ein Kommando liefert und wie sich mehrere Werkzeuge zu einer reproduzierbaren Analyse verbinden lassen. Dieser deutschsprachige Artikel fasst die wichtigsten Themen aus dem bereitgestellten Linux-Security-Material redaktionell neu zusammen und ordnet sie für den praktischen Einsatz ein.

Hinweis zur Quelle: Der Artikel ist eine eigenständige deutschsprachige Aufbereitung des bereitgestellten Materials. Er übernimmt nicht den vollständigen Originaltext. Die Beispiele dienen der Administration, Defensive Security, Analyse und Ausbildung.

1. Netzwerkverbindungen sichtbar machen

Bei einem Security-Vorfall ist eine der ersten Fragen: Welche Verbindungen bestehen aktuell und welche Dienste lauschen auf dem System? Auf modernen Linux-Systemen ist ss dafür besonders nützlich.

# Aktive TCP-Verbindungen mit Prozessinformationen
ss -tnp

# Lauschende TCP-Ports
ss -tlnp

# Alle UDP-Sockets mit erweiterten Informationen
ss -uanpe

# Nur bereits aufgebaute Verbindungen
ss -o state established

Mit lsof lässt sich die Netzwerkperspektive anschließend mit der Prozessperspektive verbinden:

# Prozesse mit Netzwerk-Sockets anzeigen
lsof -i -n -P

# Prozesse an Port 443 ermitteln
lsof -i :443

# Etablierte Verbindungen nach Prozess auflisten
lsof -i -n -P | grep ESTABLISHED

Für autorisierte Tests und die Bestandsaufnahme eigener Systeme können zusätzlich dig, whois, traceroute, mtr oder nmap eingesetzt werden. Scans gehören ausschließlich in einen klar definierten und erlaubten Scope.

2. Prozesse und verdächtige Aktivitäten untersuchen

Eine ungewöhnliche CPU-Last, ein unbekannter Prozess oder eine unerwartete Dateiöffnung können wichtige Hinweise auf Fehlkonfigurationen oder eine Kompromittierung liefern.

# Prozesse mit Details
ps aux

# Prozessbaum anzeigen
ps auxf

# Interaktive Übersicht
htop

# Prozesse nach Speicherverbrauch sortieren
ps aux --sort=-%mem | head -20

# Dateien eines bestimmten Prozesses untersuchen
lsof -p PID

Besonders interessant sind gelöschte Dateien, die von einem laufenden Prozess weiterhin geöffnet werden:

lsof | grep deleted

Das ist ein Indikator, kein Beweis für Malware. Jede Auffälligkeit muss im Kontext weiterer Artefakte bewertet werden.

3. Dateisystem und Integrität analysieren

find und grep gehören zu den wichtigsten Werkzeugen für die Untersuchung von Dateien, Berechtigungen und zeitlichen Veränderungen.

# Kürzlich geänderte Dateien suchen
find / -type f -mtime -1 -ls 2>/dev/null

# SUID- und SGID-Dateien finden
find / -type f \( -perm -4000 -o -perm -2000 \) -ls 2>/dev/null

# Weltweit beschreibbare Dateien finden
find / -type f -perm -o+w -ls 2>/dev/null

# Nach verdächtigen Mustern suchen
grep -r -i "password\|passwd\|pwd" /etc 2>/dev/null

Für Integritätsprüfungen können Hashes erzeugt und später verglichen werden:

sha256sum /pfad/zur/datei

# Beispiel für eine Hash-Liste wichtiger Systemprogramme
find /bin /sbin /usr/bin /usr/sbin -type f -exec sha256sum {} \; > system_binaries.sha256

4. Dateisystem-Zeitlinien für Forensik

Bei einer Incident-Response-Untersuchung ist die zeitliche Reihenfolge von Änderungen häufig entscheidend. Linux stellt dafür mehrere Zeitstempel bereit, darunter atime, mtime und ctime.

# Änderungszeitpunkte systematisch erfassen
find / -type f -printf "%T@ %Tc %p\n" 2>/dev/null | sort -n > filesystem_timeline.txt

# Dateien innerhalb eines Zeitfensters untersuchen
find / -type f -newermt "2026-08-01" ! -newermt "2026-08-02" -ls 2>/dev/null

Eine solche Zeitlinie sollte anschließend mit Logs, Benutzeraktivitäten und Netzwerkereignissen korreliert werden. Ein einzelner Zeitstempel ist niemals automatisch ein Beweis für eine Attacke.

5. Logs und Authentifizierungsereignisse

Logs sind eine der wichtigsten Quellen für Incident Response. Je nach Distribution und Logging-Stack unterscheiden sich Speicherort und Format. Bei Systemen mit systemd ist journalctl besonders relevant.

# SSH-Service untersuchen
journalctl -u sshd

# Ereignisse eines Zeitraums
journalctl --since "1 hour ago"

# Authentifizierungsfehler suchen
grep "Failed password" /var/log/auth.log

# Erfolgreiche Logins betrachten
grep "Accepted password" /var/log/auth.log

Eine einfache Brute-Force-Indikation kann beispielsweise über die Häufigkeit fehlgeschlagener Anmeldungen erfolgen:

awk '/Failed password/ {print $11}' /var/log/auth.log | sort | uniq -c | sort -rn

Auch hier gilt: Rate-Limits, NAT, zentrale Logging-Systeme und legitime Automatisierung können die Interpretation beeinflussen.

6. Benutzer, Gruppen und SSH-Sicherheit

Benutzerkonten und Berechtigungen bilden einen zentralen Teil der Angriffsfläche. Für ein Audit sind unter anderem UID 0, ungewöhnliche Konten, Gruppenmitgliedschaften und SSH-Konfigurationen interessant.

# Benutzer mit UID 0
awk -F: '$3 == "0" {print}' /etc/passwd

# Normale Benutzerkonten anzeigen
getent passwd | awk -F: '$3 >= 1000 {print $1, $3, $6, $7}'

# Login-Historie
last -F | head -20

# Aktive Sitzungen
w

Für SSH sollte die effektive Konfiguration geprüft werden, statt sich ausschließlich auf eine Konfigurationsdatei zu verlassen:

sshd -T | grep -E "permitrootlogin|passwordauthentication|pubkeyauthentication"

# Laufende SSH-Verbindungen
ss -tnp | grep ':22'

7. System-Hardening

Defensive Linux-Sicherheit umfasst unter anderem unnötige Dienste, Netzwerkparameter, Dateiberechtigungen, SSH und Firewall-Regeln. Änderungen sollten immer zur jeweiligen Distribution und Systemrolle passen.

# Laufende Dienste prüfen
systemctl list-units --type=service --state=running

# Listening Services prüfen
ss -tlnp

# Firewall-Regeln bei iptables-basierten Systemen prüfen
iptables -L -n -v

Kernel-Parameter wie Reverse-Path-Filtering oder bestimmte Redirect-Mechanismen können je nach Umgebung sinnvoll sein. Pauschale Hardening-Skripte sind jedoch riskant: Ein Parameter, der auf einem Server sinnvoll ist, kann auf einem Router, Container-Host oder Desktop-System Nebenwirkungen haben.

8. Incident Response: strukturiert statt hektisch

Bei einem Verdacht auf eine Kompromittierung sollte zunächst der Zustand dokumentiert werden. Eine einfache Triage kann Systeminformationen, Netzwerkverbindungen, Prozesse, Benutzeraktivität und kürzlich geänderte Dateien erfassen.

#!/bin/bash
INCIDENT_DIR="/tmp/incident_$(date +%Y%m%d_%H%M%S)"
mkdir -p "$INCIDENT_DIR"

uname -a > "$INCIDENT_DIR/system.txt"
uptime >> "$INCIDENT_DIR/system.txt"
date >> "$INCIDENT_DIR/system.txt"

ss -tunap > "$INCIDENT_DIR/network.txt"
ps auxwwf > "$INCIDENT_DIR/processes.txt"
w > "$INCIDENT_DIR/users.txt"
last -20 >> "$INCIDENT_DIR/users.txt"

find /etc /bin /sbin /usr/bin /usr/sbin -type f -mtime -1 -ls \
  2>/dev/null > "$INCIDENT_DIR/recent_files.txt"

tar czf "${INCIDENT_DIR}.tar.gz" -C /tmp "$(basename "$INCIDENT_DIR")"

In einer realen Untersuchung sollten zusätzlich Beweissicherung, Chain of Custody, zentrale Logs und gegebenenfalls ein forensisches Abbild berücksichtigt werden. Eine laufende Analyse verändert den Zustand eines Systems – das muss dokumentiert werden.

9. Kryptowährungs-Mining als Beispiel für Anomalieerkennung

Ungewöhnlich hohe CPU-Last kann unter anderem durch Cryptomining, fehlerhafte Software oder legitime rechenintensive Prozesse entstehen. Deshalb sollte nicht nur nach einem bestimmten Port oder Prozessnamen gesucht werden.

# Hohe CPU-Auslastung identifizieren
ps aux --sort=-%cpu | head -20

# Netzwerkverbindungen laufender Prozesse prüfen
ss -tnp

# Verdächtige Cron-Einträge untersuchen
for user in $(cut -d: -f1 /etc/passwd); do
  crontab -l -u "$user" 2>/dev/null | grep -E "curl|wget|python|sh" | grep -v '^#'
done

Eine belastbare Bewertung kombiniert Prozessdaten, Netzwerkverbindungen, Persistenzmechanismen, Dateisystemartefakte und Logs.

10. Speicher- und Ressourcenanalyse

Security-Kommandos können selbst erhebliche Ressourcen verbrauchen. Besonders rekursive Dateisuchen, Paketmitschnitte, Hash-Berechnungen und forensische Operationen sollten kontrolliert ausgeführt werden.

# CPU- und I/O-Priorität reduzieren
nice -n 19 ionice -c 3 find / -type f -mtime -1

# Lange laufende Befehle begrenzen
timeout 300 tcpdump -i any -w capture.pcap

# Ressourcen eines Kommandos messen
/usr/bin/time -v command

Für produktive Systeme sind außerdem Wartungsfenster, Ausgabe-Limits, Logrotation und ein Testlauf in einer Entwicklungsumgebung sinnvoll.

11. Portables Linux-Scripting

Security-Skripte sollten nicht blind davon ausgehen, dass jede Distribution dieselben Programme und Pfade verwendet. Debian/Ubuntu setzen beispielsweise auf apt und dpkg, während Red-Hat-basierte Systeme häufig dnf und rpm verwenden.

if command -v dpkg >/dev/null 2>&1; then
    dpkg -l
elif command -v rpm >/dev/null 2>&1; then
    rpm -qa
fi

if command -v systemctl >/dev/null 2>&1; then
    echo "systemd verfügbar"
fi

Auch bei sed, grep, find und anderen Unix-Werkzeugen können Implementierung und Optionen zwischen GNU- und BSD-Varianten abweichen. Portable Skripte sollten Verfügbarkeit und Optionen daher bewusst prüfen.

Fazit

Die Linux-Shell ist für Cybersecurity-Profis vor allem deshalb wertvoll, weil sie Sichtbarkeit und Automatisierung miteinander verbindet. ss liefert Netzwerkdaten, ps und lsof zeigen Prozesszusammenhänge, find und sha256sum unterstützen die Dateianalyse und journalctl sowie klassische Log-Werkzeuge helfen bei der Ereigniskorrelation.

Entscheidend ist dabei nicht die Anzahl der bekannten Befehle, sondern die Fähigkeit, aus mehreren Datenquellen belastbare Hypothesen zu bilden, Änderungen reproduzierbar zu dokumentieren und zwischen einem echten Indikator und einem normalen Systemverhalten zu unterscheiden.

Security-Grundregel: Netzwerk-Scans, Paketmitschnitte, forensische Zugriffe und Konfigurationsänderungen nur auf eigenen Systemen oder mit ausdrücklicher Autorisierung durchführen. Besonders invasive oder ressourcenintensive Befehle gehören in isolierte Testumgebungen.
